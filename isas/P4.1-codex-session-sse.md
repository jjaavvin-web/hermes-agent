## Problem

P4 (PR #42) shipped the codex sessions REST API (`/api/codex-sessions`
+ confirm-token destructive routes) but no event stream — operators
have to poll the REST endpoint to see state changes.  The dashboard
SPA tab (Wave 2) needs live updates as sessions transition through
the lifecycle (CLAIMED → EXECUTING → MERGING → COMPLETE / ESCALATED),
ISA phase moves (scaffold → verify → complete), PR meta lands, etc.

The existing `/api/pulse/stream` SSE endpoint already multiplexes
`health` probes and `pulse.activity` hive log deltas.  Adding a third
event stream (`codex.session`) onto the same connection is the
natural place — the SPA tab subscribes to one URL and filters by
event type, matching the pattern other tabs already use.

## Goal

After this ISA:

- `gateway/codex_session_events.py` ships
  `codex_session_events_iter(sessions_path, *, stop_event, poll_interval_sec)`,
  an async iterator that polls `~/.hermes/codex_sessions.json` mtime
  and yields one delta event per observed row change.
- Three event shapes: `appeared` (first observation of a thread),
  `changed` (one of state/isa_phase/pr_state/pr_number/pr_url moved),
  `removed` (thread present last tick, absent now).
- `/api/pulse/stream` consumes the iter alongside the existing
  `pulse.activity` generator, emitting events as
  `event: codex.session` SSE frames.
- Read-only / mtime-poll design: zero coupling to the dispatcher.
  The dispatcher continues to write `codex_sessions.json` as today
  and is not modified.

## Out of Scope

- Pushing events from the dispatcher (pub/sub).  Mtime-poll is
  sufficient for the human cadence of state transitions.
- A separate `/api/codex-sessions/stream` endpoint.  Multiplexing
  onto `/api/pulse/stream` matches the existing pattern.
- Slash `/status` deep-link from Discord into the dashboard tab.
  Tombstoned for Wave 2 once the SPA tab exists.

## Constraints

- **No coupling to the dispatcher.**  The iter reads
  `codex_sessions.json` only.  No imports of
  `gateway.codex_session_dispatcher`.
- **No event flood.**  The set of watched fields is intentionally
  tight (`state`, `isa_phase`, `pr_state`, `pr_number`, `pr_url`) —
  adding `last_message_at` would emit on every Discord message and
  drown the stream.
- **Resilient to missing / malformed JSON.**  File-not-found and
  parse errors must NOT crash the iter; they're warning-logged and
  the next tick re-tries.

## Decisions

**D-1 (2026-05-25): mtime poll, not pub/sub.**
The dispatcher's `_write_state` is the single chokepoint for state
changes — but adding a pub/sub callback requires plumbing through
the dispatcher constructor, the adapter wire-up, and the SSE endpoint.
An mtime poll observes the same chokepoint (the file write) without
any coupling.  At a 2 s cadence, latency is below the human-noticeable
threshold for these state transitions (one per Discord message /
phase edit / PR transition).

**D-2 (2026-05-25): tight watched-fields set.**
`state`, `isa_phase`, `pr_state`, `pr_number`, `pr_url` are the
fields a dashboard tab cares about.  Adding `last_message_at` would
emit on every Discord message — drowning the stream.  If a new field
becomes interesting, edit `_WATCHED_FIELDS` and ship a follow-up.

**D-3 (2026-05-25): multiplex onto existing /api/pulse/stream,
not a new endpoint.**
The SPA tab needs ONE connection.  Multiplexing onto the existing
stream matches the pattern other dashboard tabs already use.  No
breaking change for existing consumers — they get a new `event:
codex.session` type they can ignore.
