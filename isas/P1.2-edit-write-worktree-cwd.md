## Problem

P1.5 wired the codex per-thread worktree contextvar
(``agent.codex_session_context._active_worktree_var``) into bash
tool calls via ``tools/environments/base.py:_run_bash``.  But the
file-edit tools (``write_file``, ``patch``, ``read_file``, etc.)
have their own path resolution path through
``tools/file_tools._resolve_path_for_task``, which did **not**
consult the contextvar.

Concretely: ``_resolve_path_for_task`` falls back to
``_get_live_tracking_cwd(task_id) or TERMINAL_CWD or os.getcwd()``.
On the FIRST Edit/Write of a turn (before any bash command has
updated live tracking), relative paths resolve against the
gateway's process cwd — **the live tree, not the assigned codex
worktree**.

Discovered today (2026-05-25 PM) while verifying P1.5 end-to-end.
Silent-data-corruption risk: every codex parallel session that
quickly does a relative-path edit before any bash command would
write to the operator's live tree instead of the per-thread
worktree.

## Goal

After this ISA:

- ``tools/file_tools._resolve_path_for_task`` resolves relative
  paths using this priority:
  1. Absolute path → unchanged.
  2. **Codex per-thread worktree** (via
     ``agent.codex_session_context.get_active_worktree()``) — new.
  3. ``_get_live_tracking_cwd(task_id)``.
  4. ``TERMINAL_CWD`` env var.
  5. ``os.getcwd()``.

- The codex worktree is consulted only when the contextvar is set
  AND the resolved directory exists on disk (defense against a
  stale contextvar pointing at a deleted worktree).

- Behavior outside a codex thread (contextvar = None) is unchanged:
  resolution falls through to live tracking + TERMINAL_CWD as before.

## Out of Scope

- Adding the worktree-cwd plumbing to OTHER tool surfaces (e.g.
  patch_parser, skill_manager, code_execution).  Each uses its
  own path-resolution surface; touching them is a separate audit.
  Most go through ``write_file`` / ``patch`` which DO use
  ``_resolve_path_for_task``, so they benefit transitively.
- Surfacing the active worktree in the SPA tab or pulse stream.

## Constraints

- **Backward-compatible with non-codex flows.**  When the
  contextvar is None (default), behavior matches the pre-P1.2 path
  exactly.  Regression-tested via ``test_no_contextvar_falls_through``.
- **Defensive against stale contextvar.**  If the contextvar
  points at a deleted worktree, the resolution falls through to
  the pre-P1.2 fallbacks rather than building a phantom path.
- **No silent global cwd change.**  We never call ``os.chdir()`` —
  the contextvar is per-asyncio-task and per-process cwd is shared
  global state.

## Decisions

**D-1 (2026-05-25): codex_wt overrides live tracking.**
The contextvar carries operator intent ("this turn belongs to thread X
with worktree Y"); live tracking carries history ("the last bash
command happened to be in directory Z").  When both disagree, the
contextvar is more specific — it scopes the entire turn.  Live
tracking is still consulted as a fallback when the contextvar isn't
set (regular Discord chat).

**D-2 (2026-05-25): defensive `os.path.isdir` check.**
A stale contextvar pointing at a deleted worktree (e.g. operator
manually removed it) would otherwise build a phantom path like
``/home/josep/.hermes/codex-wt/<sid>/foo.py`` against a missing
dir — and then ``.resolve()`` would silently produce a path that
nothing handles.  Falling through to existing fallbacks instead
keeps behavior predictable.

**D-3 (2026-05-25): lazy import inside the function.**
Matches the pattern in ``base.py:_run_bash``.  Keeps the
``tools/file_tools.py`` module importable in environments without
the codex dispatcher installed (or during early bootstrap when
``agent.codex_session_context`` hasn't been imported yet).

## Changelog

  conjectured:   plumbing the contextvar into ``_run_bash`` covered
                 the typical codex flow (worker does ``cd
                 /worktree/path`` first; subsequent relative-path
                 file ops resolve via the updated live tracking)
  refuted by:    real worker behavior writes files BEFORE any bash
                 ``cd`` — the LLM's first Edit/Write of a turn
                 lands wherever the gateway's process cwd is, which
                 is the operator's live tree.  Audit caught this
                 right before unleashing Hermes parallel sessions
                 (which would have all silently scribbled on the
                 live tree)
  learned:       contextvar plumbing has to cover every surface
                 where path resolution happens.  Adding the codex
                 contextvar to bash WITHOUT also adding it to the
                 file-ops resolver is a partial fix that LOOKS
                 complete in tests but corrupts the live tree in
                 real use
  criterion now: ISC-1..ISC-5 — codex worktree resolved at the
                 file-ops layer, override priority above live
                 tracking, defensive against stale contextvar

## Handback

**Project:** ``codex-parallel-workflow-p1.2``.  **Lesson:**
contextvar plumbing must cover every surface where path resolution
happens, not just the most obvious one.  Adding the codex contextvar
to bash WITHOUT also wiring it into the file-ops path resolver is a
silent-corruption trap that LOOKS complete in tests but writes to
the wrong tree in production.

**Open follow-ups:**
- Audit other path-resolution surfaces (``patch_parser``,
  ``skill_manager_tool``, ``code_execution_tool``) — most route
  through ``write_file`` / ``patch`` which now benefit
  transitively, but a direct audit would confirm zero remaining
  gaps.
- End-to-end smoke: drive one Discord thread through a real coding
  task and verify (via ``git -C <wt> status``) that the edits land
  in the worktree.
