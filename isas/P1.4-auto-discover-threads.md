## Problem

The codex session dispatcher only allocates a session row when Discord
fires ``on_thread_create`` — which Discord does **only for threads
created while the bot is online**.  Threads that pre-exist when the
bot connects (or that were created during a gateway outage) are never
auto-tracked.

Operator hits this when:

- The bot was offline / disabled, threads were created during that
  window.
- ``HERMES_CODEX_DISPATCHER`` was enabled AFTER threads already existed
  in the configured channels.
- Fresh deployment with pre-existing Discord channels.

Discovered today (2026-05-25): operator screenshot showed 6 Discord
threads in the codex channels but the dispatcher tracked only 4 (and
one of those was an orphan from earlier testing).  Three threads
(NOTIONFORMAT, CONFIG, MOTHERSHIP) had never received an
``on_thread_create`` event and therefore had no worktree, no isa
record, no codex pipeline participation.

## Goal

After this ISA:

- ``CodexSessionDispatcher`` gains a ``discover_threads(threads)``
  method.  Input: ``list[(thread_id, channel_id, name)]``.  For each
  thread not in ``codex_sessions.json``, allocates a session row +
  worktree using the thread name as the isa slug.  Skips already-tracked
  threads silently.  Returns ``list[ReattachResult]`` with
  ``status="discovered"`` for newly-allocated sessions.

- ``on_thread_create`` accepts a new ``silent: bool = False`` kwarg.
  When True, the Discord banner post is skipped.  Used by
  ``discover_threads`` so re-discovering N existing threads doesn't
  spam Discord with N banner messages on every bot restart.

- ``gateway/platforms/discord.py:on_ready`` walks every visible guild's
  ``threads`` list after ``on_bot_restart`` and passes them to
  ``discover_threads``.  Optional ``HERMES_CODEX_DISCOVER_CHANNELS``
  env var scopes discovery to a comma-separated set of parent channel
  IDs; unset = discover every visible thread (default).

## Out of Scope

- Archived-thread discovery.  Discord's archived threads require a
  separate API call (``channel.archived_threads()``); auto-discover
  starts with active threads only.
- Renaming the discovered isa slug if it collides with another
  session's worktree branch (handled by worktree_broker's existing
  collision logic).
- Auto-discovery of new threads created mid-runtime — those still go
  through the normal ``on_thread_create`` Discord event.

## Constraints

- **Silent by default for discovery.**  N banner posts per restart
  is operator-visible spam.  Discovery never sends discord_send.
- **Per-thread error isolation.**  One failed allocation must not
  abort the rest of the discovery loop.
- **Idempotent.**  Re-running ``discover_threads`` with the same
  input set is a no-op (the second call sees the rows from the
  first as already-tracked).
- **No automatic kill.**  Discovery only ADDS rows.  Cleaning up
  obsolete rows (threads that were deleted from Discord) is a
  separate concern — out of scope here.

## Decisions

**D-1 (2026-05-25): channel allowlist via env var, not config file.**
``HERMES_CODEX_DISCOVER_CHANNELS`` slots into the existing systemd
drop-in pattern alongside ``HERMES_CODEX_DISPATCHER=1``.  Default
unset = discover everything, which matches the existing dispatcher's
behavior of not channel-filtering ``on_thread_create``.

**D-2 (2026-05-25): silent by default for discovery, not for normal
on_thread_create.**
A user-created thread should get its banner (confirms the bot saw
the thread and allocated a worktree).  A re-discovered thread on
restart should NOT — the banner adds zero new information and
operator restart is frequent during development.

**D-3 (2026-05-25): active threads only, not archived.**
Discord's archived threads require ``channel.archived_threads()``
which is paginated + rate-limited.  Operators who want to track an
archived thread can unarchive it (auto-fires ``on_thread_update``)
or run ``/spawn`` in it.  Defer the archived-discovery work.

**D-4 (2026-05-25): no auto-kill of obsolete rows.**
A row whose thread was DELETED from Discord could be auto-killed
on discovery (compare tracked-set minus visible-set).  Skipped here
because:
  (a) Discord rarely deletes threads; archive is more common.
  (b) An auto-kill could lose work if a discovery cycle runs before
      the operator has merged the worktree.
  (c) Operator can ``/kill`` manually when ready.

## Handback

**Project:** ``codex-parallel-workflow-p1.4``.  **Lesson:** when a
lifecycle relies on a third-party event (Discord ``on_thread_create``),
always provide a reconciliation hook on bot startup that compares
"observed state" to "current state."  Otherwise the system has a
permanent onboarding gap for any state that existed before the bot
came online.

**Open follow-ups:**
- Archived-thread discovery via ``channel.archived_threads()``
  pagination.
- Auto-kill of rows whose thread was deleted from Discord (compare
  tracked-set − visible-set; needs careful guards against losing
  in-flight work).
- Surface "discovered" sessions distinctly in the SPA tab (e.g. a
  "Discovered this restart" badge that clears after the first
  message).
