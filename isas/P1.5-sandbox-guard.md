## Problem

P1.2 + P1.3 made the file_tools resolver consult the codex worktree
contextvar and forward the resolved path to file_ops.  But the agent
itself can still construct an **absolute** path that escapes the
worktree:

- Agent runs ``terminal: python -c "print(os.path.abspath('foo'))"``
- Python's ``os.path.abspath`` resolves against the inner shell's
  cwd — which is the gateway's process cwd
  (``/home/josep/.local/share/hermes-agent``) NOT the codex worktree
  (because the terminal subprocess code path doesn't fully honor the
  contextvar yet)
- Agent reads "OK the absolute path is /home/josep/.local/share/hermes-agent/foo"
- Agent re-issues ``write_file`` with that ABSOLUTE path
- P1.3's resolver lets absolute paths through unchanged (correct
  for general cases — the agent might intentionally read ``~/.bashrc``)
- File lands in the live tree.

Reproduced 2026-05-26: a smoke test wrote the file correctly to the
worktree (first write) AND to the live tree (second write triggered
by agent's self-verification).

Patching every code path that touches cwd is wide surface area
(terminal subprocess, skill_manager, code_execution, patch_v4a, …).
A defense-in-depth guard at the file_tools layer makes this whole
class of bugs **loud instead of silent**: even when a future tool
escapes the contextvar, the WRITE itself is rejected with a clear
error the agent can react to.

## Goal

After this ISA:

- ``tools/file_tools._enforce_codex_sandbox(resolved_abs_path, op_name)``
  helper exists.  Returns None when the write is allowed; an error
  string when denied.
- ``write_file_tool`` consults the sandbox after path resolution and
  before any actual write.
- ``patch_tool`` (replace mode + v4a mode) consults the sandbox for
  EVERY target path before acquiring locks; v4a is all-or-nothing
  (one out-of-worktree path denies the whole patch).
- Symlinked worktree paths compare correctly via
  ``os.path.realpath`` canonicalization.
- Read operations are NOT sandboxed — reading config files outside
  the worktree (``~/.bashrc``, system files for diagnostics) is a
  normal codex worker activity.

## Out of Scope

- Sandboxing READ operations — too restrictive for typical codex
  workflows.  Agents often need to read system config or other
  parts of the filesystem.  WRITE is the dangerous primitive.
- Sandboxing the terminal/bash subprocess (a future P1.5.1 would
  ensure those subprocesses run in the worktree cwd).  This ISA
  is the FAIL-LOUD complement, not the WRITES-RIGHT fix.
- Skill manager / code execution audit.  Both routes have their
  own write paths; they'll need their own sandbox checks in
  follow-ups.  This ISA catches the highest-volume write path
  (file_tools.write_file + patch_tool).

## Constraints

- **Inert outside codex sessions.**  When the contextvar is None
  (regular Discord chat), the sandbox is a no-op.  No regression
  on existing tools.
- **Defensive against stale contextvar.**  If the contextvar points
  at a deleted directory, fall through to None (defer to the OS) —
  don't build phantom comparisons against a missing path.
- **Symlink-safe.**  Canonicalize both worktree and target via
  ``os.path.realpath`` before comparing.  A symlinked worktree
  (e.g. ``~/work -> ~/.hermes/codex-wt/<sid>``) must work.
- **Clear error message.**  The agent must be able to read the
  refusal and react.  Error includes: tool name, denied path,
  active worktree path, remediation hint ("use a relative path
  or a path inside the worktree").
- **No process-wide cwd changes.**  The sandbox checks paths;
  it never calls ``os.chdir``.

## Decisions

**D-1 (2026-05-26): sandbox at file_tools, not file_ops.**
file_tools is the chokepoint the LLM-facing tools hit.  file_ops is
the lower-level shell-executor.  Sandboxing at file_tools means we
only need to patch a handful of well-known tool entry points
(write_file, patch); patching file_ops would touch its execute
plumbing (and other in-process consumers of file_ops would lose
backward compat).

**D-2 (2026-05-26): WRITES only, READS unrestricted.**
A codex worker reading ``~/.bashrc`` or system config is normal and
useful.  A codex worker WRITING outside its worktree is the dangerous
case we're guarding against.  Mirrors the Unix permission model: read
access is broad, write access is scoped.

**D-3 (2026-05-26): clear error includes remediation hint.**
The agent reads the error and can self-correct.  The hint
("use a path relative to the worktree, or an absolute path that
starts with the worktree path") makes the right next move obvious.
The error tag ``CODEX_SANDBOX`` makes log greps + future telemetry
straightforward.

**D-4 (2026-05-26): v4a patches are all-or-nothing.**
A multi-file V4A patch where one target is outside the worktree is
rejected entirely.  Landing partial writes would leave the worker's
work in an inconsistent state — bad if the operator merges the
partial result.  Deny the whole patch; operator sees the error and
re-emits with corrected paths.

## Handback

**Project:** ``codex-parallel-workflow-p1.5``.  **Lesson:** when the
surface area of "tools that should honor a contextvar" is wide and
growing, add a single chokepoint guard that converts silent
corruption into loud refusal.  The chokepoint catches the bug we
know about AND every future variation that escapes the contextvar —
without requiring perfect contextvar discipline across every tool
the agent might invoke.

**Open follow-ups:**
- Terminal subprocess cwd: ensure ``terminal`` / bash subprocess
  runs in the worktree when a codex contextvar is active.  Would
  remove the agent's source of confusion (Python's
  ``os.path.abspath`` returning the wrong directory).
- Skill manager / code execution audit: each has its own write
  paths.  Should they also consult the sandbox?  Probably yes for
  symmetry, but blast radius is lower (they're not in the agent's
  default tool loop the way write_file/patch are).
- Sandbox telemetry: count denials per session.  A session with N>0
  denials probably has a confused agent worth flagging on the SPA
  tab.
