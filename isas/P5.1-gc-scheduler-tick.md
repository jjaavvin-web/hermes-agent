## Problem

P5 shipped `WorktreeBroker.gc(tracked_sids=...)` and
`WorktreeBroker.reap_deleted(max_age_days=7)` but never wired them
into a recurring tick.  Right now an operator has to call them by
hand — meaning orphan worktrees accumulate under
`~/.hermes/codex-wt/` indefinitely until someone notices the disk
pressure.

After P3.5 the closed-loop pipeline calls `WorktreeBroker.release(sid)`
on every successful merge, so most orphans come from edge cases:

- Operator killed a session via `/kill` before P3 / P3.5 landed.
- A bot crash mid-`on_thread_create` left a worktree without a row.
- The dispatcher row was manually removed but `release` wasn't called.

These are rare, but they accumulate.  Each orphan worktree holds a
git branch + a few hundred MB of working tree on disk.

## Goal

After this ISA, the Discord adapter starts a `CodexGcWatcher` task
alongside `CodexPhaseWatcher` (P2.5) and `CodexMergeWatcher` (P3.5).
Once per hour the watcher:

1. Reads `codex_sessions.json` to build the `tracked_sids` set.
2. Calls `broker.gc(tracked_sids=...)` — renames any orphan worktree
   into `~/.hermes/codex-wt/.deleted-<ts>/<sid>/`.  Never a real delete.
3. Calls `broker.reap_deleted(max_age_days=7)` — purges
   `.deleted-<ts>` buckets older than 7 days (recovery margin).

Each broker call is in its own try/except — a crash in one must not
skip the other or kill the loop.

## Out of Scope

- Passing a populated `live_branches` set to gc (would require
  `gh pr list --state open` per tick).  Tombstoned: defense-in-depth,
  not load-bearing.
- Operator-configurable interval / max-age.  Hardcoded defaults are
  fine on first ship; tune if the hourly cadence proves wrong.
- Per-tick metrics surfaced to the dashboard.  Logs are enough today.
- Restructuring gc / reap_deleted themselves — those landed in P5
  and are unchanged here.

## Constraints

- **No `rm -rf` or `git clean -fxd` in the watcher source.**  All
  deletion remains delegated to `WorktreeBroker.reap_deleted` which
  itself uses `shutil.rmtree` scoped exclusively to the `.deleted-<ts>`
  namespace gc owns (WORKFLOW-LESSONS §3 rule 5).
- **Tick must NOT crash the loop.**  Both `broker.gc` and
  `broker.reap_deleted` are isolated try/except; an exception logs
  a warning, the tick returns, and the next interval fires normally.
- **No `rm` of `.deleted-<ts>` buckets from the watcher itself.**
  Only `broker.reap_deleted` may delete them — the watcher must not
  shortcut around it.

## Decisions

**D-1 (2026-05-25): hourly cadence, hardcoded.**
Worktree orphans accumulate slowly (most sessions go through the P3.5
closed loop and release on merge).  Hourly gc is enough to keep
operator dashboards clean without burning CPU.  If the cadence proves
wrong (e.g. CI accumulates hundreds of orphans), make it
operator-configurable later — but YAGNI for first ship.

**D-2 (2026-05-25): no `gh pr list` for live_branches on first ship.**
The `tracked_sids` set already protects every in-flight session;
adding `live_branches` is defense-in-depth against the edge case
where a session row was deleted but the PR is still open.  Skipping
this lookup keeps the tick fast (no network) and the watcher pure-local
(no auth dependency).  Tombstoned as a follow-up.

**D-3 (2026-05-25): both calls per tick, never skip.**
gc renames; reap purges; they operate on different sets of dirs.  A
crash in one must not skip the other — the operator never gets to
the point of seeing accumulated orphans + accumulated `.deleted-<ts>`
buckets at the same time.  Both calls wrapped in their own try/except.

  criterion now: ISC-3 + ISC-4 + ISC-5 — both calls every tick,

## Handback

**Project:** `codex-parallel-workflow-p5.1`.  **Lesson:** a capability
shipped without a scheduler is a capability nobody uses.  Wire
periodic maintenance into a background loop at the same time as the
library method, not in a follow-up ISA — though if you must split it
out (because the library ISA was already big), keep the wire-up small
and disciplined.

**Open follow-ups after P5.1:**
- `live_branches` lookup via `gh pr list` (defense-in-depth, not
  load-bearing — `tracked_sids` already protects in-flight sessions).
- Operator-configurable interval + max-age.
- Per-tick metrics surfaced to the dashboard (P4 SSE territory).
