## Problem

P1.2 patched ``_resolve_path_for_task`` to consult the codex worktree
contextvar.  But the resolved path was only used for **locking** and
**staleness checks** — the actual ``file_ops.write_file(path, ...)`` /
``file_ops.read_file(path, ...)`` / ``file_ops.patch_replace(path, ...)``
calls used the **original** (often relative) path.

``file_ops`` runs its commands via ``self._exec(cmd, cwd=self.env.cwd)``
where ``self.env.cwd`` is the **live-tracking cwd** maintained by the
terminal tool.  That cwd is independent of the codex contextvar.  And
``base.py:_run_bash`` explicitly honors an explicit ``cwd=`` argument,
so the contextvar gets ignored.

Smoke test caught this 2026-05-25 ~19:24 UTC: a Discord codex thread
wrote ``codex-smoke.txt`` to ``/home/josep/workspace/`` — the live
tracking cwd — instead of the assigned codex worktree at
``~/.hermes/codex-wt/<sid>/``.

## Goal

After this ISA, the three file tools that compute a resolved path
forward it to ``file_ops`` so writes land in the codex worktree:

- ``read_file_tool``  →  ``file_ops.read_file(resolved_str, …)``
- ``write_file_tool``  →  ``file_ops.write_file(_resolved, …)``  (main branch)
- ``patch_tool`` (replace mode)  →  ``file_ops.patch_replace(_path_to_resolved.get(path) or path, …)``

The fallback branches (where the resolver itself failed) keep using
the original path — no regression for the rare unresolvable case.

## Out of Scope

- ``patch_tool`` (v4a mode): the v4a patch string embeds paths in its
  body; rewriting those is the patch parser's job, not file_tools.
  Tombstoned: a follow-up can add contextvar awareness to the v4a
  patch parser when needed.
- ``skill_manager_tool._write_file``: separate file system; mostly
  writes inside ``~/.claude/skills/`` (absolute paths), so the
  relative-path bug doesn't bite there.
- ``code_execution_tool``: uses its own subprocess wrappers with
  explicit cwd; out of scope.

## Constraints

- **Backward-compatible.**  When the contextvar is unset (regular
  Discord chat), the resolver still returns an absolute path based on
  ``TERMINAL_CWD`` or ``os.getcwd``.  Tools forward that resolved
  path — identical effective behavior, no regression.
- **No file_ops API changes.**  The fix is purely at the file_tools
  call sites; file_ops.write_file / read_file / patch_replace
  signatures unchanged.
- **No silent fallthrough.**  If ``_resolve_path_for_task`` raises,
  the existing fallback branch uses the original ``path`` — same as
  before.

## Decisions

**D-1 (2026-05-25): file_tools layer, not file_ops layer.**
Fixing this at the file_ops layer would require teaching file_ops
about the codex contextvar (and concurrent-task isolation around
``self.env.cwd``).  Fixing at the file_tools layer is a 3-line patch
per tool: the resolver already produced the right path, we just need
to pass it through.

**D-2 (2026-05-25): keep file_ops API stable.**
file_ops.write_file accepts a path and treats it as either absolute
or relative-to-env-cwd.  Passing an absolute path is already
supported; no API change required.

**D-3 (2026-05-25): tombstone v4a patch parser.**
The v4a patch format embeds paths inside the patch body
(``*** Update File: foo.py``).  Rewriting those would require parsing
the patch in file_tools, which duplicates patch_parser logic.  Left
as a follow-up for when a real codex session lands a v4a patch.

## Handback

**Project:** ``codex-parallel-workflow-p1.3``.  **Lesson:** resolver
fixes need call-site fixes.  When you absolutize a path early in a
tool call chain but the downstream call ignores it, you've fixed a
variable but not a behavior.  Always trace the resolved value through
to the actual operation; if it's not used at the operation site, the
fix is incomplete.

**Open follow-ups:**
- v4a patch parser: contextvar-aware path rewriting inside the patch
  body.  Out of scope here; opens the door if a real codex session
  needs v4a patches.
- Audit ``skill_manager_tool``, ``code_execution_tool`` — most use
  absolute paths or have their own subprocess wrappers, but worth a
  pass for completeness.
