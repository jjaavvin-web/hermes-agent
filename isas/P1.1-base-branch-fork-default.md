## Problem

The dispatcher's constructor defaulted ``base_branch="origin/main"``
since P1.  In a typical fork setup the user's local clone has TWO
remotes: ``origin`` pointing at the upstream parent (e.g.
NousResearch/hermes-agent) and ``fork`` pointing at the user's own
fork (e.g. jjaavvin-web/hermes-agent).  With the old default, every
codex worktree was allocated from upstream's ``main`` — drifted
1000+ commits from the user's actual ``fork/main`` base.

The MergeBroker (P3) pushes to ``fork`` and opens PRs against
``main`` (in the user's fork).  But the worktree's branch base is
upstream/main, which means:

- ``git rebase origin/main`` inside the worktree (during MergeBroker)
  would try to apply upstream's 1000+ commits onto fork/main —
  catastrophically unmergeable.
- Even if no rebase is performed, the PR diff would show every
  upstream-only commit as part of the worker's "work."

Discovered today (2026-05-25 PM) when auditing 4 in-flight codex
sessions found all worktrees pinned at upstream's ``dbe5d8497``,
1032 commits ahead of fork/main.  Operator reset the 4 existing
worktrees manually to ``fork/main`` (zero commits to lose since no
worker had committed yet).  This ISA fixes the default so future
sessions are born on the right base.

## Goal

After this ISA:

- ``CodexSessionDispatcher.__init__`` resolves ``base_branch`` in
  this order:
  1. Explicit constructor arg
  2. ``HERMES_CODEX_BASE_BRANCH`` env var (when non-empty)
  3. Default ``"fork/main"``
- ``None`` (the new sentinel) triggers env+default resolution.
- The docstring documents the resolution.

## Out of Scope

- Renaming the user's remotes (operator's git config, not Hermes's
  problem).
- A migration script that resets existing worktrees (already done
  out-of-band by the operator; the existing sessions had zero
  worker commits to preserve).
- Surfacing the resolved base_branch in the dashboard tab.

## Constraints

- **Explicit arg > env var > default** — operators who pass an
  explicit value at construct time keep that behavior.  Existing
  callers that pass ``base_branch=`` still work.
- **No silent ``origin/main`` fallback.**  If the env var is set
  to an invalid value, broker.allocate will surface that — better
  to fail loudly than to silently land on the wrong base.
- **Backward-compatible signature** — keyword-only arg, default
  None.  Old callers passing ``base_branch="origin/main"`` still
  work (they get explicit-value resolution).

## Decisions

**D-1 (2026-05-25): default ``fork/main`` not ``origin/main``.**
The codex parallel workflow is fork-targeted by design — MergeBroker
pushes to ``fork`` and opens PRs against ``main`` in the fork.
Worktree base must agree with that target or the rebase / PR diff
becomes meaningless.  ``origin/main`` was a P1 oversight from
mirroring upstream-style conventions where ``origin`` IS the fork.

**D-2 (2026-05-25): env var override, not config file.**
Operators with non-standard remote names (e.g. ``my-fork`` instead
of ``fork``) need an escape hatch.  Env var is the smallest possible
surface — drops into the existing systemd drop-in pattern alongside
``HERMES_CODEX_DISPATCHER=1``.  Adding to a config file would mean
another reader for a single string.

**D-3 (2026-05-25): existing worktrees fixed out-of-band.**
The 4 in-flight sessions when this was discovered had zero worker
commits (verified via reflog).  Operator used ``git reset --hard
fork/main`` per worktree to re-point them at the correct base.
No data lost.  Future sessions get the fix via this PR.

## Handback

**Project:** `codex-parallel-workflow-p1.1`.  **Lesson:** default
config values that assume a particular git remote topology are
fragile across deployments.  Always provide an env-var override
for any string that points at a specific git ref / remote — even
"obvious" defaults like ``origin/main``.

**Open follow-ups:** none for P1.1 specifically.  Existing
in-flight worktrees were corrected out-of-band; future sessions
inherit the fix.
