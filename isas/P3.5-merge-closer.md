## Problem

P1→P5 wired the factory: Discord thread → worker → ISA `phase: verify`
→ Opus peer-review → APPROVE → `MergeBroker.merge()` → PR opened with
auto-merge label.  Mergify (or the alternate Actions workflow) handles
the actual merge server-side.

**The pipeline leaks here.**  Once `MergeBroker.merge()` returns OK, the
session row is left at `state: MERGING` forever.  Nothing reacts to the
PR actually being merged.  The worktree stays allocated, the linked
Kanban card stays open, the Discord thread stays alive, and on bot
restart `on_bot_restart` sees a `MERGING` row with a worktree on disk
and treats it as a live session — confusing.

The symmetric case (PR closed unmerged by a reviewer) has no handler
either: the row is stuck at `MERGING`, the operator never gets
notified, and the next peer-review trigger has no idea the prior
attempt failed.

P3.5 closes the loop by adding a background poller that watches each
`MERGING` row's PR and dispatches the lifecycle transition:

- PR still open → no-op (next tick re-checks).
- PR merged → finalize: state=COMPLETE, release worktree,
  complete Kanban card, archive Discord thread, post closeout.
- PR closed unmerged → escalate: state=ESCALATED, post warning,
  ping operator.

## Goal

After this ISA:

- `MergeBroker.merge()` success persists `pr_number`, `pr_url`,
  `head_branch`, `classification` (label), `merge_requested_at` onto
  the row at APPROVE time (the data the watcher needs).
- A `CodexMergeWatcher` (background asyncio task, default 60 s interval)
  walks `MERGING` rows, calls `gh pr view --json state,mergedAt,mergeCommit`
  per session, and fires `on_pr_merged(thread_id)` or
  `on_pr_closed_unmerged(thread_id)` on state transitions out of OPEN.
- Dispatcher gains `on_pr_merged` + `on_pr_closed_unmerged` hooks.
  `on_pr_merged` is idempotent: re-running on a row already at
  `state: COMPLETE` is a no-op; individual side effects (worktree
  release / kanban complete / thread archive) tolerate already-done.
- `on_bot_restart` no longer clobbers `state: COMPLETE` or
  `state: ESCALATED` rows to `ORPHANED` when the worktree is gone.
- Discord adapter wires a `discord_archive_thread(thread_id)` closure
  the dispatcher can call to lock+archive a finished thread.

## Out of Scope

- GC scheduler tick (calling `WorktreeBroker.gc()` on a background
  interval) — separate one-liner follow-up.
- P4 SSE pulse events for codex session lifecycle.
- P4 SPA tab.
- Deny-list narrowing.
- Removing the now-redundant `on_thread_archive` worktree+kanban
  cleanup — that path stays as a defense-in-depth for sessions that
  bypass the PR pipeline (e.g. manually archived from Discord).

## Constraints

- **No `gh pr merge` from the watcher.**  The watcher only OBSERVES;
  merging is delegated to Mergify / the Actions workflow / a human.
  The watcher never force-merges a PR.
- **State write before side effects.**  `finalize_merged` writes
  `state: COMPLETE` to `codex_sessions.json` BEFORE attempting
  worktree release / kanban complete / Discord archive.  If a side
  effect crashes, the row is still terminal; the operator can clean
  up the residue without the watcher re-firing on the next tick.
- **Per side-effect try/except.**  Each side effect (release, kanban,
  archive, closeout post) is wrapped independently — one failure
  must not skip the next.
- **No `gh pr view` shell injection.**  The PR number is an int
  pulled from the persisted row; pass it via argv list, not a shell
  string.
- **Watcher only acts on `state: MERGING` rows with a `pr_number`.**
  Rows without a PR number (e.g. MergeBroker crashed before opening
  the PR) are skipped — operator triage.

## Decisions

**D-1 (2026-05-25): Poll, don't subscribe to a webhook.**
The MergeBroker's auto-merge path runs through Mergify or a GitHub
Actions workflow.  We could subscribe to a webhook for `pull_request`
events, but that needs a public endpoint + secret rotation +
event-loss handling.  Polling via `gh pr view` is bounded (one call
per MERGING session per minute), uses the existing `gh` auth, and is
trivially resumable across gateway restarts.  Latency is a minute,
which is fine for "PR merged → close thread."

**D-2 (2026-05-25): State write before side effects.**
The alternative (do side effects, then write state) loses idempotency
if any side effect throws — the watcher would re-fire on the next
tick.  Writing `state: COMPLETE` first is the simpler invariant:
"once the watcher commits a transition, it never re-fires," even at
the cost of leaving residue (worktree dir, open kanban card) if a
side effect crashes.  Residue is recoverable by operator; double-fire
is not.

**D-3 (2026-05-25): `on_pr_closed_unmerged` keeps the worktree.**
If a reviewer closed the PR unmerged, the operator may want to
inspect the diff, fix the issue, push a new commit, and reopen.
Releasing the worktree would force a `/revive` round-trip.  The
ESCALATED state already stops auto-reviews, so leaking the worktree
here is bounded by operator attention.

**D-4 (2026-05-25): Add `discord_archive_thread` injection rather
than reaching for the adapter's discord.py client.**
The dispatcher tests construct the dispatcher directly with mock
injections.  Reaching for `discord.py` thread objects would force
the dispatcher to know about the adapter, breaking the existing
clean injection seam.  A new `discord_archive_thread` callable
matches the `discord_send` pattern exactly.

## Changelog

2026-05-25 — original P3 scope assumed Mergify (or the operator)
  would close the loop after the PR merged
  conjectured:   "PR opened with auto-merge label" was the end of the
                 dispatcher's job — Mergify owns merge + GitHub owns
                 the thread state
  refuted by:    P3 only writes `state: MERGING` and stops; nothing
                 reverts that to COMPLETE.  On gateway restart,
                 `on_bot_restart` saw worktrees still on disk and
                 treated MERGING rows as live sessions, holding ports
                 + branch names + dashboard rows indefinitely
  learned:       "the merge broker opens the PR" and "the session is
                 closed" are two separate events.  The bridge is a
                 short poller + a dispatcher hook for the transition.
                 ~150 LOC.  Worth it.
  criterion now: ISC-1..ISC-11 — explicit watcher + finalize/escalate
                 hooks + dispatcher idempotency + restart safety

hands off to an external system (Mergify, GitHub auto-merge), the
session lifecycle does NOT end at the handoff — there's a follow-up
transition to observe and react to.  Don't leave `state: MERGING`
without a closer.
